# Індивідуальний план поглиблення контенту сторінок

Дата: 13 жовтня 2026 року. Детальні рядки всіх 38 активних URL — у `SEO_CONTENT_GAP_MATRIX.csv`.

## Пріоритети та критерій рішення

1. **P1 — комерційні сторінки рішень:** `/solutions`, `/integrations`, `/pricing`, `/hotel-booking-calendar`, `/hotel-check-in`, `/hotel-operations`, `/guest-communication`, `/hotel-automation`. Нижній інформаційний блок у цих сторінках був коротким; додані розділи відповідають на практичні запитання, яких не було в основній демонстраційній подачі.
2. **P2 — сторінки довіри/дії:** `/about`, `/registration`. Вже дають підтверджений біографічний контекст, формат запиту та межі реєстрації; додатковий текст створив би повтори.
3. **NO SEO FOOTER — контактні/службові сторінки:** `/contact`, `/privacy`, `/offer`, `/refunds`. Їхня задача — контакт або умови, тож довгий пошуковий текст не потрібен.
4. **Основний контент замість нижнього блоку:** статті, кейси, блог, кейс-хаб і інструменти вже мають змістовне тіло. Не додаємо штучний SEO-підвал; у кейсах першочергово потрібні власницькі докази, згадані в E-E-A-T аудиті.
5. **Головна:** лишити як коротку навігаційну/product landing сторінку. Розширений сценарій і відповіді вже розміщені вище по сторінці; новий блок дублював би його.

## Зміст виконаних розширень

| URL | Додана відповідь | Внутрішні переходи |
|---|---|---|
| `/solutions` | Оцінювання повного сценарію, питання для демонстрації, робота з винятками | календар, заселення, операції, тарифи |
| `/integrations` | Склад/напрям даних, контрольний тест бронювання, зміни та скасування | календар, тариф, кейс звірки; наявний гід iCal |
| `/pricing` | Порівняння повної вартості за однаковим сценарієм, список витрат і умов | інтеграції; наявний гід із вибору PMS |
| `/hotel-booking-calendar` | Наскрізна перевірка запису, щоденні контрольні точки й винятки | календарна стаття, операції, заселення, інтеграції |
| `/hotel-check-in` | Покрокова підготовка та план для збоїв/винятків | календар, комунікація, housekeeping |
| `/hotel-operations` | Єдині значення статусів, відповідальні, handoff і фізична перевірка | housekeeping стаття, заселення, кейс |
| `/guest-communication` | Карта повідомлень за етапом проживання, ручна ескалація й тест | заселення, автоматизація, підготовчий гід |
| `/hotel-automation` | Малий пілот і вимірювання процесу до/після без обіцянки ROI | інтеграції, заселення, комунікація, стаття автоматизації |

## Канібалізація та редакційні межі

- Сторінки рішень пояснюють продуктову задачу та критерії перевірки; повні інструкції лишаються в статтях, на які ведуть відповідні мости.
- `/integrations` не перетворюється на каталог гарантовано сумісних OTA; фактичну сумісність перевіряємо для об’єкта.
- `/pricing` не вигадує умови trial, зміну/скасування чи платежі поза опублікованою таблицею; читачеві дається список того, що треба підтвердити.
- `/hotel-check-in` не обіцяє повного unattended check-in для будь-якого готелю й відділяє технологічний сценарій від вимог країни.
- `/hotel-operations` не прирівнює статус прибирання до дозволу заселення.
- `/hotel-automation` не перераховує хвилини в прибуток без окремої моделі.
- Кейсові метрики/твердження не розширюються без першоджерела, періоду та знаменника.

## Перевірка після редагування

Технічні перевірки: синтаксис модулів, активний content SEO audit, серверний route/media/link audit, повний `node --test`, `git diff --check`. Також порівняти сторінкові підрозділи та перелінковку з матрицею; перевірити, що статті/кейси не отримали повторного абстрактного блоку. Візуальну перевірку на мобільному production у цьому SEO-завданні не можна вважати валідацією нової локальної версії: ці локальні зміни ще не опубліковані, а локальний браузерний сервер недоступний у sandbox.

Деплой не є частиною цього плану. Після окремого релізу повторити URL Inspection, Rich Results Test, production canonical/sitemap і мобільне візуальне QA; для performance/Search Console та пошукового попиту потрібен доступ власника.
