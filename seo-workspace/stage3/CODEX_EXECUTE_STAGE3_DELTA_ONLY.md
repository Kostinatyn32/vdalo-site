# CODEX MASTER RUN: SEO Stage 3, content + internal linking only

Працюй **у поточному репозиторії VDALO**, а не в окремо згенерованому сайті. Етапи SEO №1 і №2 за словами власника вже виконано. **Не повторюй повний аудит, не змінюй метадані, JSON-LD, canonical, sitemap, hreflang, дизайн чи стратегію без чітко доведеного критичного блокера.** Мета: написані тексти Stage 3 впровадити ТІЛЬКИ там, де вони додають корисну інформацію, із природними посиланнями. Це вже готові редакційні тексти-кандидати; не потрібно генерувати їх з нуля.

## 0. Source of truth

1. Існуючі файли в `/seo-workspace/`, особливо поточна execution queue, page execution logs, internal-link matrix, реєстр реалізації та PAGE reports. Пошукай фактичні шляхи, не створюй дублікати.
2. Поточний код route/content/locale-компонентів у репозиторії, `PROJECT_DATA.yaml`, `data/BUSINESS_FACTS.yaml`, поточний контент і актуальні бізнес-докази.
3. Цей пакет: `seo-workspace/stage3/CONTENT_MANIFEST.json`, `content/*.md`, `CONTENT_REGISTER.csv`.
4. При конфлікті поточний код + підтверджені факти важливіші за драфт Stage 3. Виниклу суперечність зафіксуй, не перезаписуй робочу інформацію.

## 1. Режим

`DELTA-ONLY`, `SEQUENTIAL_BY_EXISTING_QUEUE`, `NO_DEPLOY`, `PRESERVE_UI`, `MINIMAL_TESTS_PER_PAGE`. Продовжуй **по всіх** 38 URL, не зупиняючись після однієї, поки дозволяє сесія та не виникло блокера; зберігай progress after each page. Починай з першої незавершеної сторінки за поточною, а не архівною чергою.

**Не змінюй готовий блок лише заради того, щоб вставити текст із пакета.** Новий draft є доповненням, не обов'язковою заміною.

## 2. Для КОЖНОЇ сторінки

1. Знайди route source, контентні компоненти, чинний мовний варіант і поточний статус виконання. Прочитай тільки зміст цієї сторінки та її конкретний plan, без нового keyword research чи загальносайтового аудиту.
2. Зроби **content diff** з відповідним `content/*.md` із маніфесту. Якщо корисна інформація вже є, познач `ALREADY_DONE` після перевірки наявних посилань, не редагуй.
3. Якщо Master Plan зазначає `NO`, не створюй SEO-блок. Постав `SKIPPED` із конкретною причиною **після** перевірки стану в репозиторії; не прибирай реальний корисний контент.
4. Якщо новий текст має інформаційну цінність, адаптуй його мінімально до чинного основного контенту, дійсних бізнес-фактів, форми звертання, мови та версії продукту. **Не додавай вигаданих функцій, тарифів, інтеграцій, клієнтів, результатів, рейтингів чи гарантій.** Якщо інформації недостатньо, залиш `BLOCKED` із переліком бракуючих доказів; не публікуй непідтверджені тези.
5. Встав блок у нижній частині `<main>` перед footer, зберігши чинні місця CTA, семантику, дизайн-систему, форми, responsiveness. Використовуй наявний SEO-content компонент, якщо він є. Не додавай нових анімацій/залежностей. H2/H3 мають відповідати ієрархії на реальній сторінці.
6. Перевір кожне Markdown-посилання draft за фактичним маршрутом/канонікалом і approved link matrix. У DOM мають бути звичайні доступні для сканування `<a href>`. Якщо посилання вже є в релевантному контексті, **не дублюй**; якщо ціль не канонічна/не доступна, **не вставляй** і запиши issue.
7. Для кейсу (`/cases/*`) перевір доказовий характер основного матеріалу. Не вставляй загальний «коментар до методики», якщо він маскує відсутність реального кейсу. Якщо кейс є дослідженням, назви це дослідженням; якщо демо, не називай роботою клієнта.
8. Для податкової теми не вводь ставок, відсотків чи категоричних юридичних висновків без поточного офіційного джерела та фахової перевірки.
9. Перевір **тільки потрібний QA**: HTML/H2, links, duplicates, mobile 360–390 px, a11y focus/readability, CTA, лінтер, відповідні тести / build (один build може бути накопичений, якщо зміни незалежні й це дозволяє архітектура). Після останньої сторінки виконай один global scoped link/content QA для внесених змін.
10. Онови **вже існуючі** реєстр, поточну чергу, журнал та link matrix тільки за фактичною зміною. Не використовуй `DONE` без проходження тестів, `ALREADY_DONE` без перевірки існуючого коду. Додай page-level record: path, reused/delta sections, links added, files changed, tests, blockers, status.
11. Збережи checkpoint до переходу на наступну сторінку.

## 3. Ідемпотентність

Перед вставкою шукай збіги H2, схожий за змістом блок та існуючі outbound links. Не додавай SEO-секцію двічі і не переписуй корисний наявний текст. Зберігай існуючий header, hero, footer, global CSS та перформанс бюджет.

Якщо CTA знаходиться в кінці сторінки, не відділяй SEO-текстом CTA від форми/конверсії без UX-підстави. Обирай порядок `основний контент → розділ → фінальний CTA → footer` або `основний контент → CTA → розділ → footer` відповідно до наявної композиції.

## 4. Статуси

- `DONE`: content delta реально внесено, перевірки пройдено.
- `ALREADY_DONE`: перевірена наявна секція та лінки повністю вирішують задачу, жодних змін не треба.
- `SKIPPED`: новий блок не має сенсу, причина в логові.
- `BLOCKED`: конкретна відсутність фактів, доступу або помилка тестів, описана в логові.
- `PENDING`: потребує роботи/перевірки. **Ніколи не перетворюй PENDING на DONE лише через існування файлу в `stage3/content/`.**

## 5. Мінімальний підсумок після всіх сторінок

Виведи кількість checked/ALREADY_DONE/NEW/UPDATED/LINKS_ADDED/SKIPPED/BLOCKED, змінені файли коду, тести, список проблем та наступний checkpoint. Побудуй коротку таблицю `URL | Було | Зроблено | SEO-блок | Посилання | QA | Статус` без припущень. **Не деплой.**

Якщо середовище завершилося перед кінцем, поверни next path зі збереженого progress і продовжуй із нього в наступній сесії без повторного аудиту.
